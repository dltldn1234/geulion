# 설계 원칙과 결정

이 문서는 GEULION v0.1의 상위 설계 결정과 근거를 기록합니다. 세부 문법과 타입 규칙은 각각의 전문 문서에서 정의합니다.

## 규범 표현

**MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, **MAY**는 규범 요구 수준을 나타냅니다. 대문자로 쓰인 곳에서만 RFC 2119의 의미를 적용합니다. ([RFC 2119](https://www.rfc-editor.org/rfc/rfc2119))

## 결정

### LD-001 — 한국어 우선이되 문법은 형식화한다

**상태: Specified**

키워드와 진단은 한국어를 우선합니다. 다만 소스 코드는 자유 문장이나 조사 생략 추론을 허용하지 않는 형식 문법을 따릅니다. 공백·기호·키워드의 구조가 구문을 결정하며 자연어 문맥이나 실행 시점의 휴리스틱으로 구문을 추측하지 않습니다.

**근거:** Lexer와 Parser가 같은 입력을 언제나 같은 토큰·구문 구조로 해석할 수 있어야 합니다. 한국어 문장처럼 보이는 자유 형식보다 명확하고 학습 가능한 규칙을 우선합니다.

### LD-002 — 명시적 의미와 정적 타입을 기본값으로 한다

**상태: Specified**

변수 초기화, 함수 매개변수 타입, 함수 반환 타입을 명시적으로 다룹니다. 허용되는 추론은 타입 문서에서 한정합니다. 타입 사이 암시적 변환, JavaScript식 truthiness, 동적 이름 탐색은 허용하지 않습니다. 의도적인 변환은 문법으로 드러나야 합니다.

**근거:** 한국어 문장 해석이나 백엔드의 coercion에 따라 타입과 실행 결과가 달라지지 않게 합니다.

### LD-003 — 가독성은 짧은 표기보다 우선한다

**상태: Specified**

선언, 블록, 조건, 반환의 경계를 눈으로 확인할 수 있어야 합니다. 키워드는 의미가 하나로 고정되어야 하고, 조사 변형이나 임의의 동의어를 문법으로 허용하지 않습니다. 생략은 문서화된 타입 추론 등 제한된 규칙에서만 허용합니다.

**근거:** 여러 자연어 표현을 같은 구문으로 받아들이면 자동 포매팅, 오류 위치 표시, 코드 리뷰와 문법 구현이 불안정해집니다.

### LD-004 — 백엔드는 구현 대상이지 의미론의 주인이 아니다

**상태: Specified**

초기 백엔드는 JavaScript/TypeScript 생태계와 연동합니다. 언어 사양은 먼저 플랫폼 독립적인 값, 평가 순서, overflow, 비교와 진단을 정의합니다. 백엔드는 그 의미를 보존해야 하며 JavaScript의 암시적 변환이나 객체 모델을 GEULION 기본 규칙으로 노출하지 않습니다. 백엔드별 동작 차이는 명시적 FFI 경계에 한정하고 FFI는 v0.1에서 연기합니다.

**근거:** 동일한 GEULION 프로그램이 향후 WebAssembly 또는 네이티브 백엔드에서도 같은 관찰 가능한 결과를 내야 합니다.

### LD-005 — 정수와 실수는 서로 다른 의미를 가진다

**상태: Specified**

정수는 signed 64-bit two's-complement 범위에서 checked exact arithmetic을 하고, 실수는 IEEE 754 binary64 의미를 갖습니다. 두 타입 사이에 자동 승격을 하지 않습니다. JavaScript `Number`를 정수의 사양으로 삼지 않으며, JavaScript 백엔드는 `bigint` 표현과 매 연산의 범위 검사를 따라야 합니다. 실수에서 정수로 바꾸는 동작은 명시적 `정수로` 호출에서만 허용합니다.

### LD-006 — 유니코드 동작은 런타임 버전에서 독립시킨다

**상태: Specified**

식별자 문자 집합, 정규화, 예약어 비교, 소스 위치는 언어 버전이 고정한 Unicode 규칙에 따릅니다. 구현은 런타임 내장 Unicode 데이터가 다르다는 이유로 허용 식별자나 토큰 위치를 바꾸면 안 됩니다. 문자열 값 정규화와 식별자 정규화는 분리합니다.

**구체 규칙:** v0.1은 Unicode 18.0.0의 `XID_Start`/`XID_Continue`를 사용하고 default-ignorable 및 bidi 제어 문자를 제외합니다. 이름 비교 전에 NFC를 적용하고 원본 철자는 진단용으로 보존합니다. 문자열 값은 정규화하지 않습니다.

**근거:** 사용자 환경·Node.js·JavaScript 엔진의 Unicode 데이터 버전 차이가 식별자 해석에 영향을 주지 않게 합니다. XID 속성은 [Unicode UAX #31](https://www.unicode.org/reports/tr31/), NFC는 [Unicode UAX #15](https://www.unicode.org/reports/tr15/)의 18.0.0 데이터에 고정합니다.

### LD-007 — 언어 기능과 구현 상태를 분리해 표시한다

**상태: Specified**

문서에서 규칙을 정의한 것만으로 기능이 구현된 것은 아닙니다. 구현 상태는 코드가 존재하고 검증을 통과했을 때만 **Implemented**로 표시합니다. v0.1 범위를 벗어난 기능은 **Deferred**, 아직 결정이 필요한 설계는 **Proposed**로 표시합니다.

### LD-008 — 기본 매개 타입은 대괄호 표기를 쓴다

**상태: Specified**

v0.1의 기본 매개 타입은 `목록[정수]`, `사전[정수]`, `선택[문자열]`처럼 대괄호로 표기합니다. `<`와 `>`는 비교 연산자로만 남겨 타입 닫기 기호와 비교식 사이에서 토큰을 다시 나누는 문맥 의존 규칙을 만들지 않습니다. 사용자 정의 제네릭은 v0.1 범위가 아닙니다.

**근거:** Lexer가 항상 동일한 longest-match 토큰화를 사용하고 Parser가 타입 문맥에 따라 `>` 토큰을 분할하지 않도록 합니다. 목록 리터럴·인덱싱도 대괄호를 사용하지만 타입 문맥은 선언의 `:` 또는 함수 반환부 `->`로 결정됩니다.

### LD-009 — v0.1은 단일 실행 프로그램으로 시작한다

**상태: Specified**

한 `.geul` 파일에는 top-level 함수만 선언합니다. 프로그램에는 정확히 하나의 `함수 시작() -> 없음`이 있어야 하며 실행은 그 본문에서 시작합니다. 모듈 전역 값, 최상위 실행 문장, import/export, library-only 모드는 v0.1에서 연기합니다.

**근거:** 모듈 초기화 순서와 전역 변경 상태를 정의하지 않고도 재귀/상호 재귀, 변수, 제어 흐름, 타입 검사를 완결할 수 있습니다. 다중 파일/라이브러리 지원은 v0.1 의미론을 바꾸지 않는 모듈 규칙으로 후속 설계합니다.

## v0.1 우선순위

**v0.1 목표 범위:** 기본 스칼라 타입, 변수와 상수, 산술/비교/논리 표현식, 함수, 조건문과 반복문, lexical scope, 타입 검사, 기본 오류 진단. 이 목록은 목표 범위이며, 각 기능이 **Specified** 또는 **Implemented** 상태라는 뜻이 아닙니다.

**Deferred:** 클래스/상속, 사용자 정의 제네릭, 패턴 매칭, 매크로, 동시성/비동기 실행, 사용자 정의 연산자, 수동 메모리 관리, FFI, 모듈/패키지 시스템, 함수 오버로딩과 기본 매개변수.

이 우선순위는 기능이 **Implemented**라는 뜻이 아니며, v0.1 명세와 이후 구현 작업의 범위를 나눕니다.
